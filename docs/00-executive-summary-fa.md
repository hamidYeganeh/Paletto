# خلاصه‌ی اجرایی فارسی معماری و نقشه‌راه پالتو

**وضعیت:** طرح پیشنهادی برای تأیید  
**تاریخ:** ۳۰ مرداد ۱۴۰۵  
**محدوده:** صرفاً مستندسازی؛ هنوز هیچ قابلیت جدیدی پیاده‌سازی نشده است.

## تصمیم اصلی

همه‌ی قابلیت‌های موردنظر پالتو در معماری نهایی دیده شده‌اند، اما به‌صورت نسخه‌های قابل‌انتشار `v1` تا `v6` عرضه می‌شوند. نسخه‌ها بازنویسی جداگانه نیستند؛ هر نسخه روی همان هسته‌ی مشترک ساخته می‌شود.

آدرس عمومی صفحات محصول نسخه‌دار نمی‌شود. برای مثال صفحه‌ی اثر همیشه مسیر پایداری مانند `/artworks/...` دارد. `v1` و `v2` نام انتشار محصول هستند. فقط API در صورت نیاز با مسیرهایی مانند `/api/v1` نسخه‌بندی می‌شود.

## معماری پیشنهادی

```text
وب مشتری و پنل ادمین با Next.js
                |
        API تراکنشی مستقل
       NestJS + Fastify
                |
     Modular Monolith دامنه‌محور
                |
 PostgreSQL + Redis + Object Storage
                |
 Workerهای مستقل برای کارهای پس‌زمینه
```

چرا از ابتدا microservice نه؟ چون فروش اثر یکتا، رزرو، پرداخت، مالکیت و تسویه به سازگاری قوی نیاز دارند. microservice در شروع، distributed transaction و هزینه‌ی عملیاتی اضافه می‌کند. ماژول‌ها از روز اول مرز روشن، قرارداد و event دارند تا هر بخش در صورت نیاز واقعی بعداً جدا شود.

### اجزای اصلی

- `apps/web`: سایت مشتری، SEO، صفحات اثر و تجربه‌های سه‌بعدی؛
- `apps/admin`: پنل عملیات، بررسی آثار، پرداخت، اختلاف، ارسال و مزایده؛
- `apps/api`: منبع اصلی منطق تراکنشی و مجوزهای دسترسی؛
- `apps/worker`: پردازش تصویر، اعلان، جست‌وجو، reconciliation و jobهای زمان‌بندی‌شده؛
- PostgreSQL: منبع قطعی سفارش، مالکیت، قیمت، پرداخت و ledger؛
- Redis: صف، rate limit و cache موقت، نه منبع قطعی پول یا مالکیت؛
- Object Storage: فایل اصلی خصوصی، تصاویر عمومی بهینه و مدارک غیرقابل‌دست‌کاری؛
- API providerها: درگاه پرداخت، احراز هویت، پیامک و حمل‌ونقل پشت interfaceهای قابل‌تعویض.

## اصول غیرقابل‌مذاکره

1. مبلغ در دیتابیس همیشه عدد صحیح ریال است؛ تومان فقط ورودی/نمایش است.
2. یک اثر یکتا هرگز نمی‌تواند هم‌زمان دو بار رزرو یا فروخته شود.
3. redirect مرورگر اثبات پرداخت نیست؛ callback امضاشده یا استعلام لازم است.
4. ledger، bid، ownership، certificate و audit log بعد از ثبت ویرایش نمی‌شوند؛ اصلاح با رکورد جبرانی انجام می‌شود.
5. هر عملیات retryپذیر باید idempotent باشد.
6. اطلاعات ملی، بانکی، آدرس و مجموعه‌ی خصوصی وارد log عمومی یا search نمی‌شوند.
7. سرویس‌های خارجی نباید نقطه‌ی شکست اصلی بازار داخل ایران باشند.
8. AI می‌تواند پیشنهاد بدهد یا مورد مشکوک را علامت بزند، اما گواهی اصالت نهایی صادر نمی‌کند.

## ترتیب انتشار

| نسخه | خروجی اصلی                                                                       | چرا در این ترتیب است؟                                              |
| ---- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `v0` | معماری، امنیت، دیتابیس، ledger، audit، outbox، CI و عملیات                       | قبل از دریافت پول واقعی باید زیرساخت بازیابی و پیگیری آماده باشد   |
| `v1` | بازار منتخب: هنرمند و اثر واقعی، خرید ثابت، پرداخت، ارسال، گواهی و پنل ادمین     | کوچک‌ترین نسخه‌ای که خرید امن را کامل می‌کند                       |
| `v2` | پنل هنرمند/گالری، پیشنهاد قیمت، سفارش ساخت، لجستیک و تسویه‌ی حرفه‌ای             | عملیات دستی v1 را قابل‌مقیاس می‌کند                                |
| `v3` | پیشنهاد شخصی، جست‌وجوی تصویری، AR، گالری سه‌بعدی، محتوا و PWA                    | تجربه‌ی بصری فعلی را به موتور تبدیل کاربر به خریدار تبدیل می‌کند   |
| `v4` | مالکیت، provenance، گزارش وضعیت، فروش مجدد، ارزش‌گذاری و wanted list             | بازار ثانویه بدون سابقه‌ی مالکیت و اعتماد قابل‌انتشار نیست         |
| `v5` | مزایده‌ی مدیریت‌شده، KYC پیشنهاددهنده، deposit، proxy bid و anti-sniping         | به ledger، پرداخت، مالکیت و بازار ثانویه‌ی نسخه‌های قبل وابسته است |
| `v6` | B2B، اجاره/چرخش، پروژه‌های معماری، پوشش کشوری، API داده و فروش بین‌المللی قانونی | پیچیده‌ترین عملیات و وابستگی‌های حقوقی/تجاری را دارد               |

## مهم‌ترین نیازهای بازار ایران که در معماری حل شده‌اند

- تبدیل صریح تومان/ریال و تست خطای ده‌برابری؛
- شماره موبایل `+98`، OTP و محدودیت سوءاستفاده؛
- احراز هویت فروشنده و تطبیق حساب بانکی؛
- تاریخ جلالی در UI و UTC در سیستم؛
- جست‌وجوی یکسان برای `ی/ي`، `ک/ك`، ارقام و نیم‌فاصله؛
- آدرس، کدپستی و محدوده‌ی خدمات ایران؛
- callbackهای تکراری یا دیرهنگام درگاه؛
- reconciliation روزانه‌ی درگاه، ledger و تسویه؛
- بسته‌بندی، گزارش وضعیت و زنجیره‌ی تحویل اثر؛
- حق انصراف، مرجوعی، خسارت و اختلاف به‌صورت policy versioned؛
- صورت‌حساب و داده‌ی موردنیاز سامانه‌ی مؤدیان پس از تأیید مشاور مالیاتی؛
- مجوزهای تجارت الکترونیکی/فرهنگی پس از تعیین طبقه‌بندی حقوقی؛
- moderation، کپی‌رایت و حق استفاده از تصویر اثر؛
- زیرساخت قابل‌دسترسی از ایران و fallback برای سرویس‌های خارجی؛
- صادرات و پرداخت بین‌المللی فقط پس از مجوز و بررسی تحریم/گمرک.

## ترتیب فنی تسک‌های شروع

بک‌لاگ شامل ۲۲۷ تسک/فعالیت شناسه‌دار است. شش اسپرینت اول باید به این ترتیب باشند:

1. مرزبندی ماژول‌ها، امنیت، پول، مجوزها، مدل ledger و RTL؛
2. outbox، queue، audit، auth، عملیات و تست؛
3. اسکلت قابل‌استقرار API/worker/admin و یک جریان مصنوعی end-to-end؛
4. هنرمند، اثر، واحد فیزیکی، رسانه و جست‌وجوی فارسی؛
5. رزرو، سفارش و ledger با درگاه fake؛
6. درگاه واقعی، callback، reconciliation و صف ادمین.

تا زمانی که اسپرینت پنجم سازگاری رزرو/پول را ثابت نکرده، توسعه‌ی گسترده‌ی UI فروشگاه نباید جلوتر از هسته‌ی تراکنشی حرکت کند.

## معیار آماده‌بودن v1

- صفر فروش دوباره‌ی یک اثر در تست هم‌زمانی و beta؛
- تمام پرداخت‌ها و تسویه‌ها یا reconcile شده‌اند یا case مشخص دارند؛
- حداقل ۳۰ هنرمند تأییدشده، ۲۰۰ اثر واقعی و ۳۰ سفارش تکمیل‌شده در cohort اولیه؛
- هر اثر فروخته‌شده مدارک لازم condition/custody/certificate را دارد؛
- فرآیند خسارت، مرجوعی و اختلاف قابل‌اندازه‌گیری است؛
- حقوقی، مالی، امنیت، دسترس‌پذیری و عملیات release gate را تأیید کرده‌اند.

## تیم مرجع و زمان‌بندی

برای برنامه‌ی فعلی، تیم مرجع شامل یک lead، سه backend، دو frontend، یک QA automation، محصول/طراحی و پشتیبانی پاره‌وقت DevOps، حقوقی، مالی و عملیات هنری است.

با این ظرفیت، کل دامنه تقریباً ۱۴ تا ۱۸ ماه کار دارد و فقط نسخه‌ی بعدی باید تاریخ قطعی بگیرد. با دو یا سه مهندس، همین برنامه احتمالاً بیش از دو سال زمان می‌برد. کم‌کردن تعداد نفرات ترتیب معماری را تغییر نمی‌دهد؛ فقط مدت انتشارها را افزایش می‌دهد.
